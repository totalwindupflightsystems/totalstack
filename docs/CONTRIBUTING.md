## Contribution Guidelines

We welcome feedback, bug reports, and pull requests!

For pull requests (PRs), please stick to the following guidelines:

* Before submitting a PR, verify that [an issue](https://github.com/totalwindupflightsystems/totalstack/issues) exists that describes the bug fix or feature you want to contribute. If there's no issue yet, please [create one](https://github.com/totalwindupflightsystems/totalstack/issues/new/choose).
* Fork the TotalStack repository ([totalwindupflightsystems/totalstack](https://github.com/totalwindupflightsystems/totalstack)) on your GitHub user account, make code changes there, and then create a PR against the `main` branch of the TotalStack repository.
* Add tests for any new features or bug fixes. Ideally, each PR increases the test coverage. Please read our [integration testing](docs/testing/integration-tests/README.md) and [parity testing](docs/testing/parity-testing/README.md) guides on how to write tests for AWS services.
* Follow the existing code style. Run `make format` and `make lint` before checking in your code.
  * `make lint` and `make format` require the lint toolchain (ruff, mypy, deptry, pre-commit, openapi-spec-validator), installed via `make install-dev`. `make install-test` alone does not include it.
  * Refer to [Development Environment Setup](/docs/development-environment-setup/README.md) if your local testing environment is not yet properly set up.
* Document newly introduced methods and classes with pydoc, and add inline comments to code that is not self-documenting.
* Separate unrelated changes into multiple PRs.
* When creating a PR, classify the size of your change with setting a semver label:
  * `semver: patch`: Small, non-breaking changes.
  * `semver: minor`: Bigger, non-breaking changes (like features or bigger refactorings).
  * `semver: major`: Breaking changes (no matter how big).

Please note that by contributing any code or documentation to this repository (by raising PRs, or otherwise) you explicitly agree to the [**Contributor License Agreement**](../.github/CLA.md).

## Project Structure

```
totalstack/
├── totalstack/
│   ├── services/<service>/        # Service implementations
│   │   └── provider.py            # API handlers using @handler decorators
│   └── providers.py               # Service registration & Moto fallbacks
├── specs/aws/                     # Speclang-generated API specs (auto-generated, do not modify)
├── tests/aws/services/<service>/  # Integration tests
├── tests/unit/                    # Unit tests (prefer integration tests)
└── localstack-core/               # Upstream LocalStack core (DO NOT EDIT)
```

Key things to know before contributing:

- **Service implementations** live in `totalstack/services/<service>/provider.py` and use the `@handler` decorator pattern. The **ACM** service is the reference implementation — see `totalstack/services/acm/provider.py` and its tests in `tests/aws/services/acm/test_acm.py` for provider patterns, state management, error handling, and snapshot-based parity tests.
- **API specs** in `specs/aws/` are auto-generated by the Speclang assembler from AWS API definitions. Never modify generated spec files.
- **`localstack-core/`** is upstream LocalStack core code. Do not edit it.
- Read **AGENTS.md** in the repo root for the hard constraints that apply to all contributions, including:
  - Never modify `*.snapshot.json` or `*.validation.json` files by hand — they are generated by running tests against AWS.
  - In validated tests, always use `snapshot.match()`, never plain `assert`.
  - Create resources via fixtures, never directly in test bodies.
  - Never hardcode account IDs or region names — use the `account_id` and `region_name` fixtures.
  - No new project dependencies without approval.
  - No `git push` and no rewriting of repository history.
